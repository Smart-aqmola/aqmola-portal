# Адреса, услуги и поставщики

26 октября 2026 года пользователь согласовал локальный справочник фронтенда, отказ `422 not_serviced` для неизвестного/несовпадающего адреса, подбор только для своего подтверждённого объекта и исключение заблокированных поставщиков.

## Данные и поиск

В PostgreSQL добавлен `Address`: `id`, `territoryId`, `locality`, `street`, `without`, служебный `searchText`. Поля соответствуют тестовому `account/data/address-directory.ts`; названия населённых пунктов и улиц хранятся на ru/kk. Снимок содержит 33 вымышленные записи; идентификаторы сохранены как во фронте. Это улицы, а не реестр домов; номер дома и квартиры задаётся в объекте отдельно. Общая унификация прежних идентификаторов каталога с UUID остаётся отдельной задачей.

`GET /api/v1/addresses/search?q=...&lang=ru&territoryId=...` — публичный поиск, до восьми результатов, стабильная сортировка по id. Язык ru/kk, ru по умолчанию. Запрос до 200 знаков, каждый поисковый фрагмент должен присутствовать; учитываются регистр, повторные пробелы и ё/е. Ищутся оба языка, результат выводится в выбранном языке. Пустой запрос даёт `[]`. Ответ соответствует `AddressSuggestion` фронта: `id`, `territoryId`, `locality`, `street`, `label`, `without`.

Миграция: `202610260001_addresses`. Из папки `backend` можно выполнить `pnpm db:seed:addresses`: команда обновляет только адресный справочник, не меняет роли, пользователей, организации и их территории. Территории должны быть загружены основным seed. Повторная загрузка не создаёт дубликатов. Основной `db:seed` также включает адреса.

## Подбор

`GET /api/v1/properties/:id/services?lang=ru` требует Bearer-сессию и возвращает массив `SectorService` фронта:

```json
[
  {
    "sector": "electricity",
    "state": "served",
    "providers": [
      {
        "id": "akmola-grid",
        "name": "Электросети Акмолы",
        "sector": "electricity",
        "territories": "all"
      }
    ]
  },
  { "sector": "gas", "state": "no_network", "providers": [] }
]
```

В реальном ответе всегда пять записей в порядке: `electricity`, `water`, `heat`, `gas`, `waste`. `served` означает наличие активного поставщика нужной отрасли, обслуживающего территорию (либо всю область); `no_network` — сеть отсутствует в справочнике, даже если поставщик работает по всей области; `no_provider` — сеть не исключена справочником, но доступного поставщика нет. Для двух последних состояний список поставщиков пуст. `ProviderInfo` содержит только поля фронта: id, локализованное имя, отрасль, территории; административные поля не раскрываются.

Чужой/отсутствующий объект даёт одинаковый `404 not_found`, неподтверждённый — `403 forbidden`. Идентификатор пользователя берётся из сессии. `addressId` не считается доказательством: сервер сверяет территорию, населённый пункт и улицу с записью, допуская варианты ru/kk. Несовпадение или неизвестный id даёт `422 not_serviced` без запасного подбора по территории. Если id не задан, допускается только единственное точное совпадение нормализованных названий внутри территории; неизвестный или неоднозначный адрес также даёт 422. Клиент не передаёт наличие сетей, организацию или разрешённые отрасли. Изменение основной формы сбрасывает подтверждение и закрывает подбор до новой проверки.

`GET /api/v1/properties/:id/services/:code?lang=ru` дополнительно проверяет конкретный код существующей услуги каталога. При доступном поставщике возвращается карточка услуги в прежнем формате каталога, без служебного searchText. Неизвестный код — `404 service_not_found`; услуга другого поставщика, отсутствующей сети или заблокированной организации — `422 not_serviced`. Для просмотра общего каталога сохраняются `GET /services` и `GET /services/:slug`.

Проверки читают объект, справочник и поставщиков в одной транзакции RepeatableRead. Ответы объектов не кэшируются. Это проверка на момент чтения, не резервирование доступа: будущая подача заявления должна повторить её в своей транзакции записи. Просмотр не создаёт заявлений и не пишет журнал изменений.

## Границы

Это согласованная локальная модель доступности пяти коммунальных отраслей, а не подтверждение подключения конкретного дома. Уличный тестовый справочник не описывает исключения отдельных домов, реальные технические условия и актуальные сети. Для промышленного использования нужны официальный адресный источник и зоны/данные поставщиков с точностью до дома.

Заявления ещё не реализованы. Проверка не создаёт их и не заменяет проверки будущих заявлений. Контакты, требования, документы и способы подписания поставщика из расширенного общего контракта здесь не выдумывались: пока выдаётся существующий ProviderInfo фронта. Подключение экранов к API не выполнено, исходный domain фронта не менялся.
