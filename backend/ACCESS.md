# Роли и права доступа

Реализован третий пункт локального плана. Источники: ТЗ 2.6–2.7, 12.3, 13.5, 19.1; `docs/api-contract.md`, `organization/domain/scope.ts` и `admin/domain/config.ts` фронтендера.

23 октября 2026 года пользователь согласовал основу: роли и блокировки меняет только `system_admin`; сотрудники работают внутри своей организации; `organization_admin` роли не назначает. Согласованы административные маршруты пользователей, организаций и реестр своих сотрудников с проверкой `version`.

## Полномочия реализованных методов

| Роль                                                                                                         | Свой профиль | Своя организация | Свои сотрудники | Роли и блокировки |
| ------------------------------------------------------------------------------------------------------------ | ------------ | ---------------- | --------------- | ----------------- |
| `resident`, `representative`, `tenant`, `lawful_user`                                                        | Да           | Нет              | Нет             | Нет               |
| `provider_employee`, `contact_operator`, `request_specialist`, `inspector`, `meter_specialist`, `accountant` | Да           | Да               | Нет             | Нет               |
| `organization_admin`                                                                                         | Да           | Да               | Да              | Нет               |
| `system_admin`                                                                                               | Да           | Нет              | Нет             | Да                |

Сотруднику нужна `organizationId`. Гражданские категории не дают доступа к чужой недвижимости: право на конкретный объект будет подтверждаться отдельно, в следующем этапе.
Системный администратор не получает автоматического доступа к кабинету поставщика. Совмещать `system_admin` с ролью сотрудника или организацией нельзя. Это разделяет управление порталом и действия от имени поставщика (ТЗ 13.5).
Роли сотрудников одной организации можно совмещать. У пользователя только одна организационная привязка, как в текущем контракте `User`.

## Методы

Все адреса имеют префикс `/api/v1`, требуют `Authorization: Bearer <token>` и возвращают стандартную ошибку `{ error: { code, message, fields? } }`.

| Метод | Адрес                      | Полномочия                                             |
| ----- | -------------------------- | ------------------------------------------------------ |
| GET   | `/admin/users`             | Только `system_admin`                                  |
| PATCH | `/admin/users/:id`         | Только `system_admin`                                  |
| GET   | `/admin/organizations`     | Только `system_admin`                                  |
| PATCH | `/admin/organizations/:id` | Только `system_admin`                                  |
| GET   | `/org`                     | Сотрудник активной организации                         |
| GET   | `/org/staff`               | Только `organization_admin` своей активной организации |

Реестры принимают `page` и `pageSize` (от 1 до 100, по умолчанию 20) и возвращают `{ items, total, page, pageSize, pageCount }`.
`/admin/users` и `/org/staff` возвращают записи пользователя с `roles[]`, `status`, `version`, именами и организацией. Это проекция `User`, а не единый документ `AdminConfig.staff` фронта.
ИИН полностью скрыт, телефон маскируется, email не возвращается. Получение полного своего профиля остаётся в `/me`.
Организация для `/org` и `/org/staff` определяется только по серверной сессии; передавать другую организацию параметром нельзя.

Изменение пользователя:

```json
{
  "version": 1,
  "roles": ["resident", "accountant"],
  "organizationId": "идентификатор-организации",
  "status": "active"
}
```

Кроме `version`, нужно передать хотя бы одно изменяемое поле. Статус — `active` или `blocked`. Для снятия всех служебных ролей одновременно передайте `organizationId: null`.
Организация обязана существовать. Непустая организационная привязка без служебной роли недопустима.

Блокировка организации:

```json
{ "version": 1, "blocked": true }
```

Устаревшая версия возвращает 409 `stale`, недостаток прав — 403 `forbidden`, неверные поля — 400 `validation_error`.
Разрешения повторно проверяются внутри транзакции изменения. Все изменения доступа, увеличение версии, отзыв сессий и запись журнала выполняются атомарно.

## Блокировки и сессии

- Изменение ролей, организации или статуса пользователя отзывает все его текущие сессии. После изменения нужен новый вход, в том числе если администратор изменил собственные права.
- Заблокированный пользователь не проходит проверку сессии и не получает новую сессию через вход по коду.
- Блокировка организации отзывает текущие сессии её сотрудников и закрывает организационные методы. После нового входа личный профиль доступен, но кабинет организации остаётся закрыт до разблокировки.
- Блокировка организации не блокирует доступ сотрудников другой организации и не скрывает общедоступный каталог.
- Разблокировка не восстанавливает ранее отозванные сессии.
- Нельзя заблокировать или лишить роли последнего активного системного администратора. Проверка защищена общей блокировкой PostgreSQL от одновременных изменений.

Роли и привязка берутся из базы на каждом запросе. Клиентские заголовки и поля формы не могут повысить права.
`user.roles` содержит роли ТЗ, а совместимое поле `session.role` принимает `resident`, `operator` или `admin`; для сотрудника также возвращается `session.organizationId`.

## Первый системный администратор

Общих паролей, предустановленной административной учётной записи и публичного метода выдачи прав нет.
Сначала зарегистрируйте локального пользователя обычным способом. Затем из папки `backend/` выполните:

```powershell
pnpm admin:bootstrap --user-id <UUID-зарегистрированного-пользователя>
```

Команда работает только в локальном режиме разработки. Она принимает существующего активного пользователя без организации, отказывает при наличии активного системного администратора, фиксирует отдельное действие `bootstrap_system_admin` и отзывает старые сессии пользователя. После команды нужно войти заново.
В основной базе эта команда автоматически не выполнялась: выбор конкретного пользователя остаётся за оператором проекта.

## Проверки и границы этапа

Тесты ролей создают отдельную случайно названную базу PostgreSQL, применяют все миграции, проверяют две организации и удаляют только созданную тестовую базу. Локальный пользователь PostgreSQL должен иметь право создавать базы.

Проверяются все 12 ролей, изоляция организаций, маскировка данных, запрет самостоятельного повышения прав, неверные комбинации ролей, конфликт версий, журнал, отзыв сессий, блокировки, безопасная первая выдача роли и одновременное снятие административных прав.

Методы недвижимости и проверки документов реализованы: [VERIFICATION.md](VERIFICATION.md). Методы договоров, показаний, начислений и платежей ещё не реализованы. При их добавлении серверные выборки должны проверять пользователя, организацию, отрасль и территорию по правилам `organization/domain/scope.ts`. Этот этап не заменяет проверки доступа к будущим ресурсам и распределение действий специалистов по будущим бизнес-процессам.
