# Черновик заявления на заключение договора

Первый подпункт этапа заявлений: создание, сохранение и восстановление своего черновика. Подачи, присвоения номера, обработки поставщиком и ЭЦП здесь нет. Источники: `docs/api-contract.md`, `contracts/domain/contract.ts`, `storage.ts`, `contract-services.ts` фронтендера (ветка dev, прочитана 27 октября 2026).

## API

Все пути имеют префикс `/api/v1`, требуют Bearer-сессию и возвращают `Cache-Control: no-store`.

- `POST /contract-applications` с `{ propertyId, serviceSlug, lang? }` создаёт черновик и возвращает 201. `lang` — ru/kk, ru по умолчанию. Объект должен принадлежать пользователю и быть подтверждён; услуга должна существовать в каталоге, соответствовать точной паре услуги/поставщика из фронта и быть доступной по адресу. Проверки выполняются внутри транзакции создания; неизвестный адрес/нет сети/неподходящий поставщик — `422 not_serviced`, чужой объект — `404 not_found`, неподтверждённый — `403 forbidden`.
- `GET /contract-applications?page=1&pageSize=20` возвращает только свои черновики: `{ items, total, page, pageSize }`, размер страницы до 100.
- `GET /contract-applications/:id` восстанавливает свой сохранённый черновик. Чужой, отсутствующий и не находящийся в статусе draft объект даёт одинаковый `404 not_found`; роли системного администратора и сотрудника не открывают черновики других людей.
- `PUT /contract-applications/:id` с `version` и изменяемыми полями сохраняет черновик, увеличивает версию и возвращает 200. Метод объединяет переданные поля с сохранёнными, в том числе внутри `applicant`, `meter`, `consents`. Пустая строка очищает поле. Пустое изменение — `400 validation_error`, устаревшая версия — `409 stale`. Версия обязательна, целое число от 1.

Пример сохранения незаконченной формы:

```json
{
  "version": 1,
  "applicant": { "email": "unfinished@" },
  "previousContract": "",
  "meter": { "has": true, "serial": "", "reading": "1," },
  "notifyBy": "email",
  "consents": { "personalData": false, "terms": false }
}
```

Неполные и временно неверные текстовые значения допустимы в черновике. Проверяются структура, типы и верхние границы из storage фронта: ФИО до 80, телефон до 30, email до 120, дата rightSince до 12, лицевой счёт до 20, предыдущий договор до 200, номер прибора до 60, показания до 30 знаков. Это не проверка готовности к отправке: обязательность, форматы, даты, документы и согласия должны полностью проверяться при будущей подаче. `notifyBy` — только cabinet/email/sms, значения согласий и meter.has — настоящие boolean, без приведения строк.

## Поля и хранение

Для формы используются имена фронта: `serviceSlug`, `sector`, `serviceTitle`, `providerName`, `rightSince`, `previousContract`, `notifyBy`, `history`. Соответствия общему контракту: `rightSince` — rightStartDate, `previousContract` — номер/текст предыдущего договора (не выдуманный UUID), `notifyBy` — notifyChannel, `history` — история статуса. Дополнительно возвращается настоящий `serviceId` каталога. Domain фронта не менялся; интеграция его репозитория с API остаётся отдельной работой.

Ответ содержит `id`, `ownerId`, `propertyId`, `serviceId`, `providerId`, поля формы, `status: "draft"`, пустые `signatures`, первоначальную запись `history`, `version`, `createdAt`, `updatedAt`. Номера и submittedAt нет. ID владельца, адрес, тип объекта, основание, отрасль, услуга и поставщик берутся с сервера; отправлять их в PUT нельзя. Нельзя прислать статус, номер, историю, подпись или время регистрации.

В PostgreSQL используется `ContractApplication` с ограничивающими внешними ключами на пользователя, объект, услугу и организацию. Содержимое черновика хранится отдельно в `draft: { payload, updatedAt }`; API разворачивает payload в плоскую форму фронта. На этом этапе разрешён только статус draft; остальные известные статусы контракта присутствуют в enum для последующих этапов, но переходов API нет.

При создании профиль и объект заполняют поля формы, после чего они являются снимком на момент создания. Пользователь может менять контактные/текстовые поля applicant, но ИИН привязан к его учётной записи: возвращается маской `900101••••56`, клиент может повторить эту же маску или свой исходный ИИН без изменения личности. Полный ИИН не дублируется в черновик, ответы и журнал. Изменение идентичности через applicant.iin отвергается. При подключении UI поле ИИН должно использовать серверную идентичность: демопроверка фронта, ожидающая полный ИИН в браузере, не является готовой проверкой для этого API.

Загрузка файлов заявления на договор будет отдельной частью. Пока attachments всегда пуст, принимается только `[]`, а имена/размеры фиктивных документов и ссылки на документы объекта не считаются вложениями заявления. Подписи не принимаются и не имитируются. Согласия в черновике сохраняют только выбор формы и не делают его поданным или подписанным.

## Защита и границы

Создание и сохранение журналируются одной транзакцией с изменением. Журнал содержит статус, версии и имена изменённых разделов, без содержимого полей и персональных данных. Параллельные сохранения одной версии дают один успех и один `409 stale`. Лимит 60 заявлений на учётную запись взят из MAX_CONTRACTS фронта и проверяется с блокировкой пользователя; одновременные запросы его не обходят. Повторный POST создаёт новый черновик: идемпотентная отправка заявления будет отдельным действием, она не реализована.

Сервер повторно проверяет пользователя и сессию в транзакции. Выдача ролей и блокировки организаций сериализованы с созданием черновика через общую блокировку управления доступом. При последующей потере доступности услуги или изменении недвижимости черновик остаётся доступен для сохранения работы, но его снимок не обновляется и не даёт права подачи. Перед будущей отправкой нужны повторная проверка недвижимости, услуги, приложений, согласий, подписей и актуализация/проверка снимка объекта.

Разрешены шесть точных пар из фронтенда: электричество для жителя, вода для жителя, тепло, газ, ТБО города и районов. В текущем старом локальном каталоге присутствуют только четыре из этих услуг: electricity-contract-resident, gas-contract, waste-contract-kokshetau, waste-contract-region. Для water-contract-resident и heat-contract пока возвращается `404 service_not_found`; данные и коды этих услуг не придумывались и старый каталог не заменялся. Бизнес-услуги и произвольные услуги поставщика нельзя использовать вместо этих заявлений.

Это серверный черновик, а не заключённый договор. Экран фронта к нему пока не подключён. Подача, регистрационный номер, вложения заявления, статусы поставщика, реальные уведомления и ЭЦП остаются следующими подпунктами.
