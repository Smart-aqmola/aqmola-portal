# Инструкция для бэкенд-разработчика

Читай этот файл первым. Он написан и для человека, и для ИИ-ассистента: структура жёсткая, термины определены, каждое утверждение можно проверить по указанному файлу.

## 1. Что это и что от тебя нужно

**Проект.** Региональный портал цифровых коммунальных услуг Акмолинской области. Житель регистрируется, добавляет объект недвижимости, заключает договоры с поставщиками (вода, свет, тепло, газ, вывоз мусора), передаёт показания счётчиков, получает единую квитанцию и платит, подаёт обращения. Сотрудник организации ведёт свой кабинет, системный администратор настраивает портал. Источник требований — техническое задание (ТЗ); номера пунктов ТЗ стоят в скобках по всей документации.

**Что уже есть.** Готов весь фронтенд (Next.js 16, React 19, TypeScript strict, CSS Modules, pnpm). Сервера и базы нет: все данные тестовые, лежат в коде и в `localStorage` браузера. Интеграции (ЭЦП, гос. вход, SMS, платёжный шлюз, электронные обращения) — заглушки, они ничего не отправляют наружу.

**Что нужно сделать тебе.** Построить API и хранилище, а затем заменить заглушки на фронте вызовами API. Дизайн, тексты, формы, проверки и статусы уже есть и протестированы; ты их не придумываешь, а переносишь на сервер и делаешь настоящей защитой (фронт защитой не является).

## 3. Как запустить фронт

```bash
pnpm install
pnpm dev            # http://localhost:3000, дальше /ru, /kk
pnpm check          # format, lint, typecheck, unit-тесты, build
pnpm test:e2e       # сценарии в браузере (порт 3100)
```

Демо-вход: на `/ru/sign-in` — телефон любого зарегистрированного жителя и код `123456`; кнопки «Войти как оператор» (выбор организации) и «Войти как администратор». Язык интерфейса: `ru`, `kk` (английский работает по адресу `/en`, но в переключателе скрыт).

## 4. Архитектура фронта в трёх строках

```
страница → load-*.ts → репозиторий (интерфейс в domain/) ← заглушка в data/     // справочные данные
компонент ui/ → хук use-*.ts → createLocalStore → localStorage                   // данные пользователя
domain/ — чистые функции и типы: проверки, статусы, переходы (без React)
```

- Зависимости: `ui` → `domain` ← `data`. Папка `domain/` не знает о React и о браузере, её можно переиспользовать на сервере (TypeScript) или читать как спецификацию.
- Все пользовательские строки лежат в словарях `src/shared/i18n/dictionaries/{ru,kk,en}.json`. Тексты ошибок для людей приходят из них; от сервера нужны **коды**, а не текст (см. раздел 7).

## 6. Рекомендуемый порядок работ

Идти слоями; после каждого слоя включать соответствующие экраны и прогонять `pnpm test:e2e`.

1. **Основа:** формат ошибок, версии объектов, журнал, роли и проверка прав (раздел 7). Без этого дальше не строить.
2. **Вход и профиль:** регистрация, код из SMS, сессия, роли `resident`/`business`/`operator`/`admin` (сейчас четыре демо-роли; полный список ролей ТЗ 2.6 — в api-contract.md).
3. **Справочники:** территории, адреса, услуги, организации, поставщик по адресу.
4. **Объекты недвижимости и подтверждение права** (Property).
5. **Заявление и договор:** ContractApplication → Contract, подписи, файлы (`POST /attachments`), переходы статусов.
6. **Приборы, показания, заявки по приборам:** с проверками показаний и автоматическим изменением приборов при закрытии заявки.
7. **Начисления, квитанция, платежи:** шлюз, уведомления шлюза, идемпотентность.
8. **Обращения.**
9. **Уведомления** (серверные, по расписанию) и **журнал**.
10. **Кабинет организации, админка, отчёты.**
11. **Афиша, опросы, обратная связь** (`GET /events`, `GET /surveys`, `POST /surveys/:slug/votes`, `POST /feedback`): один голос на человека, ограничение частоты для формы. Погода и курс валют для панели «Мой регион» (`/my-region`) — тоже с сервера (кэш внешнего источника).
12. **Реальные интеграции** (ЭЦП, SMS, шлюз, электронные обращения) — по очереди, за интерфейсами.

Маршруты предложены в api-contract.md (раздел «Маршруты»). Это предложение: меняй, но тогда правь контракт и пиши фронтендеру.

## 7. Правила, которые сервер обязан соблюдать

1. **Права только на сервере.** Фронт прячет экраны, но защитой это не является (ТЗ 2.7, 19.1). Организация видит только свои данные: договоры по `providerId`, обращения по `organizationId`, заявки и показания по отрасли и территории, платежи только по своим строкам (`organization/domain/scope.ts` — готовая логика). Заблокированная организация (`AdminConfig.blockedOrganizations`) в кабинет не входит.
2. **Статусы и переходы — таблицы в `domain/`.** Они перечислены в api-contract.md. Сервер проверяет допустимость перехода и роль, которая его делает. Нельзя перескочить статус и нельзя закрыть без обязательной причины или результата (отказ, запрос сведений, закрытие заявки по прибору).
3. **Проверки на сервере повторяют фронтовые.** Показания (`meters/domain/reading.ts`: разрядность, не меньше предыдущего, не в будущем, не старше 45 дней, дубль, фото для электричества и газа), заявление и документы по основанию (`contracts/domain/contract.ts` + `AdminConfig`), платёж (`billing/domain/payment.ts`: нельзя платить услугу, пока по ней есть незавершённый платёж).
4. **Идемпотентность.** Заявление, показания и платёж принимают `Idempotency-Key`. Повторное уведомление шлюза не зачисляет платёж дважды: каждое уведомление несёт свой идентификатор, принятые хранятся в `Payment.notices[]` (ТЗ 9.17).
5. **Версия объекта.** `version` растёт при изменении; несовпадение ожидаемой версии — `409 stale` (ТЗ 4.19). Фронт для заявок это уже понимает.
6. **Ошибки.** Тело `{ "error": { "code", "message", "fields?" } }`. Для интерфейса важен **код** (фронт сам берёт текст на ru/kk из словаря), `message` — запасной понятный текст без технических деталей (ТЗ 18.8). Не отдавать трассировки и внутренние имена.
7. **Журнал.** Каждое изменение статуса, подписи, показаний, платежа, настроек пишется: кто, когда, что было и что стало (ТЗ 12.7, 13.4, 19.7). Записи только добавляются. Формат — `AuditEntry` в api-contract.md.
8. **Деньги.** Целые тенге (или тиыны), одно решение на весь API. Портал начисления **не меняет**, а показывает данные поставщика (ТЗ 9.7). Если свежих данных нет, `available: false` и последние известные суммы. Данные карты на портал не попадают никогда (ТЗ 9.19).
9. **Персональные данные.** ИИН и телефон маскируются там, где не нужны целиком; ссылки на файлы подписанные и короткоживущие (ТЗ 19.4–19.5). В тестовой среде данные вымышленные, реальные ПДн в репозиторий не класть.
10. **Языки.** `ru` и `kk`. Тексты, которые вводит администратор (шаблоны уведомлений, названия), приходят в обоих языках.

## 8. Поведение демо, которое нужно сохранить или осознанно изменить

- Номера: `DEMO-POK-ГГГГ-NNNNN` (показания), `DEMO-ZPR-…` (заявки по приборам), `DEMO-PAY-…` (платежи), `DEMO-OBR-…` (обращения), `DEMO-DOG-…` (заявления на договор), `ЭО-ГГГГ-NNNNN` (электронные обращения). Боевой формат нужно согласовать (открытый вопрос, ТЗ 4.10, 8.8).
- Оператор вывоза мусора в заглушке всегда «молчит» (нет свежих данных) — для проверки ветки ТЗ 9.8.
- Уведомления на фронте **строятся из историй** заявок, договоров, показаний, платежей и обращений (`notifications/domain/notifications.ts`), отдельного списка нет. С бэкендом они приходят с сервера, а события «срок передачи показаний» (с 20-го числа) и «приближается поверка» (за 60 дней) создаются сервером по расписанию.
- Сейчас подпись (ЭЦП) — демо-отметка; настоящую проверку делает сервер.
- Отчёты: фронт считает 18 показателей и CSV из данных браузера; XLSX и PDF — заглушки. На сервере все три формата.
- Афиша и опросы: тестовые данные, даты событий считаются от понедельника текущей недели, сроки опросов — от сегодняшнего дня, чтобы демо не устаревало. С сервера приходят настоящие даты. «Билеты» не продаются — кнопка честно об этом говорит.
- «Мой регион»: погода и курс USD/EUR/RUB — **демо-значения, вычисленные от даты** (`region/domain/signals.ts`), с пометкой на странице. Внешние API фронт не вызывает (политика безопасности разрешает запросы только к своему адресу), поэтому эти данные должен отдавать сервер.
- Карта в контактах — нарисованная схема и ссылка на OpenStreetMap: встраивать карту 2ГИС/Яндекс можно только после изменения политики безопасности (CSP) в `next.config.ts`.
- Номер обращения из формы обратной связи: `DEMO-FB-ГГГГ-NNNNN`.

## 9. Как подключать API, не ломая интерфейс

1. Выбери один хук (например `use-payments.ts`). Сохрани его публичную форму (что возвращает и какие функции даёт).
2. Внутри замени `createLocalStore` на запросы (SWR/React Query или собственный слой — **любой новый пакет сначала согласуй с фронтендером**, правило проекта).
3. Домен (`domain/*.ts`) оставь как есть: он нужен для проверок до отправки и для подсветки ошибок. Когда сервер вернул код ошибки, фронт покажет текст из словаря.
4. Модульные тесты хука и e2e-сценарии должны проходить без правок. Если пришлось менять тест — это сигнал, что форма данных изменилась; обсуди.
5. Данные кабинета организации и админки сейчас целые коллекции. На сервере нужны постраничные выборки с фильтрами (`GET /org/...`, `GET /admin/...`, `GET /reports`).

## 10. Как проверить, что готово

Приёмка — пять сценариев из [test-cases.md](test-cases.md), они же Playwright-тесты `tests/e2e/scenarios.spec.ts`:

1. Заключение договора: от регистрации до скачивания договора.
2. Передача показаний.
3. Пломбирование счётчика.
4. Единая квитанция и оплата.
5. Обработка обращения.

Плюс `pnpm check` без ошибок и автопроверка доступности `tests/e2e/axe.spec.ts` (WCAG 2.2 AA) — она идёт в общем `pnpm test:e2e`, новые страницы и ответы сервера не должны её ломать. Не покрыто фронтом и остаётся на тебе: нагрузка, резервное копирование, настоящие интеграции, серверные права, безопасность каналов (ТЗ 14, 15, 19–20).

## 12. Для ИИ-ассистента

- Источник истины по полям и статусам: `docs/api-contract.md`, затем `src/features/<фича>/domain/*.ts`. Не выдумывай поля, статусы и коды; если чего-то нет, спроси человека.
- Не меняй `domain/` фронта без согласования: на нём стоят тесты. Ошибки пиши кодами, а не текстом.
- Не добавляй зависимости без согласования. Правила проекта — `AGENTS.md` (в нём важное предупреждение: версия Next.js новая, читай `node_modules/next/dist/docs/` перед правкой кода фронта).
- Перед сдачей любого куска: `pnpm check` и, если затронут интерфейс, `pnpm test:e2e`.
