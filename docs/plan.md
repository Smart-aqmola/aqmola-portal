# План: тестовый фронт портала Aqmola

Статус: первая версия (этапы 1–10) выполнена. Добавлена вторая часть по техническому заданию (этапы 11–19, 2026-10-21). План уточнён по исследованию astana.kz ([docs/research/astana-kz.md](research/astana-kz.md)). Основа дизайна — `design/variants/1-panorama.html`.

Решения после исследования (2026-10-20):

- Афишу мероприятий в первую версию **не берём**.
- Опросы и 3D-туры — **после первой версии** (раздел «Позже» внизу).
- Тёмная тема и режим для слабовидящих — в **этап 10**.
- Услуги для жителей и бизнеса **разделяем переключателем** «Жителям / Бизнесу» (параметр адреса `for=resident|business`, по умолчанию «Жителям»).

Решения от 2026-10-21 (по техническому заданию):

- **Английский язык отставлен.** Новый английский текст не пишем, в переключателе языка его не показываем. Словарь `en.json` и его тесты пока не удаляем, чтобы не ломать сборку; полное удаление — отдельным решением.
- **Делаем только фронт.** Бэкенд скоро начнёт писать. Все данные идут через репозитории-заглушки; в этапе 11 фиксируем контракт для бэкендера: сущности, поля, статусы, маршруты.
- **Интеграции — заглушки с пометкой.** ЭЦП, вход через гос. механизмы, SMS, платёжный шлюз, проверка ИИН, справочник адресов, выгрузка XLSX/CSV от сервера: в интерфейсе есть кнопка или экран, данные тестовые, рядом пометка «демо». Реальных вызовов нет.

## Цель первой версии

Рабочий фронт на тестовых данных: все пользовательские сценарии портала для жителей, бизнеса и операторов, три языка, телефон и десктоп. Без сервера и базы: данные отдаёт слой-заглушка, который позже заменяется на API без переписывания страниц.

## Структура

```
src/
  app/[lang]/                 # страницы
    page.tsx                  # главная (Панорама)
    services/                 # каталог, фильтры, поиск
    services/[slug]/          # карточка услуги
    services/[slug]/apply/    # демозаявка
    situations/[slug]/        # жизненная ситуация
    applications/             # мои заявки
    applications/[id]/        # заявка, статус, история
    operator/                 # кабинет оператора (демо)
    news/, news/[slug]/       # новости
    tourism/, tourism/[slug]/ # места
    about/                    # о регионе и о проекте
  features/
    catalog/                  # услуги, ситуации, организации, территории
    applications/             # заявки, статусы, история
    content/                  # новости, места, «скоро»
    each: domain/ (типы, правила) · data/ (репозиторий: интерфейс + заглушка) · ui/ (компоненты)
  shared/
    ui/                       # шапка, подвал, кнопки, карточки, иконки
    i18n/                     # словари ru.json, kk.json, en.json, выбор языка
    styles/                   # токены, базовые стили
tests/e2e/                    # Playwright
```

Правило зависимостей: `ui` → `domain` ← `data`. Страницы получают данные только через репозитории.

- ✅ Передача показаний (7.1): объект → услуга → прибор, предыдущие показания и дата, ввод, дата снятия, фото с камеры или из галереи (7.2), подтверждение достоверности. Проверки до отправки (7.5): отрицательное, формат, разрядность, дубль, период (не старше 45 дней, не раньше предыдущих), фото там, где его требует поставщик (демо: электричество и газ). Уменьшение показаний (7.7) спрашивает подтверждение и уходит на проверку. Распознавание по фото (7.4) — демо-экран с подстановкой значения, модуля нет.
- ✅ Статусы показаний (7.9) и история (7.13) с комментарием поставщика; пользователь видит, учтено ли значение в начислениях (7.12). Решения поставщика — демо-панель на карточке показания. Статус «черновик» в списке есть, демо его не выдаёт.
- ✅ Заявки по приборам (8.2–8.6): одна форма с разными полями для каждого вида (`requestForms` в `meter-request.ts`), удобные даты (до трёх), файлы, статусы, карточка заявки с историей. Демо-панель исполнителя (8.8): принять, запросить сведения, назначить дату и специалиста, изменить дату с причиной, внести результаты и закрыть, отклонить. Закрытие заявки меняет приборы человека: новый прибор, «заменён», пломба, срок поверки, неисправность. Акт (8.10) скачивается текстовым файлом с пометкой «демо».

### Этап 17. Начисления и оплата (ТЗ 9) ✅

- ✅ Раздел «Начисления и оплата» (`/billing`) с четырьмя частями: начисления, единая квитанция, оплата, история платежей. Вкладка «Начисления» в меню кабинета и плитка на главной включены.
- ✅ Начисления по объекту (9.1–9.3): выбор объекта и месяца (шесть последних), вид «сводно по всем услугам» (таблица с итогом) или «по каждому поставщику» (карточка с 13 полями ТЗ 9.2). Данные дают репозиторий и заглушка `features/billing/data/stub-charge-repository.ts`: суммы выдуманы по id объекта, поставщику и месяцу, поэтому не прыгают между визитами; в цепочке месяцев есть долг, пени, перерасчёты и переплата. Поставщики объекта — по адресу, первый из списка в каждой отрасли (демо; с бэкендом — по действующему договору).
- ✅ Нет свежих данных (9.8): тестовый оператор ТБО «молчит» 12 дней, показываются последние суммы, дата обновления и плашка «Данные временно недоступны», оплата этой услуги закрыта.
- ✅ Единая квитанция (9.4, 9.5, 9.9): плательщик, адрес, месяц, по каждой услуге начисление, долг, перерасчёты и пени, оплачено, итого, общая сумма, способы оплаты. Прошлые месяцы доступны, скачивается текстовый файл с пометкой «демо» (PDF сделает бэкенд).
- ✅ Оплата (9.10–9.14, 9.19): выбор услуг с итогом и способ (шлюз, банковское приложение, ссылка или идентификатор), один платёж на выбранные услуги с распределением по поставщикам и лицевым счетам. Услугу нельзя оплатить дважды, пока платёж по ней не завершён. Данные карты фронт не просит и не хранит.
- ✅ Платежи (9.15–9.18): восемь статусов ТЗ, история, страница платежа с распределением, подтверждением оплаты (текстовый файл) и демо-панелью платёжного сервиса. Повторное уведомление шлюза ничего не меняет (9.17), оплаченный платёж уменьшает остаток в начислениях.
- Не сделано: раздельная оплата по схемам разных шлюзов поставщиков (9.13, 9.14) — это интеграция, фронт хранит поставщика и счёт отдельно в каждой строке платежа, чтобы сервер мог разнести деньги.

### Этап 18. Мои заявки, обращения, уведомления, кабинет организации (ТЗ 10–12, 16)

Подэтапы: **18а** единый реестр заявок ✅, **18б** обращения ✅, **18в** уведомления ✅, **18г** кабинет организации.

- ✅ 18а. «Мои заявки» (`/applications`) собирает в один список услуги каталога, заявления на договоры, заявки по счётчикам и обращения (10.1, 10.2). Карточка с полями ТЗ 10.3: номер, дата и время подачи, вид, объект, организация, описание, статус, исполнитель, срок рассмотрения по регламенту (демо: `REGULATION_DAYS`, просрочка отмечена), комментарий организации, число документов, результат (10.6). История и скачивание документов — на странице каждой заявки по ссылке «Открыть». Фильтры по виду и состоянию (в работе, ждут действия, архив) и поиск; закрытые остаются в архиве (10.7). Возвращённое заявление, вопрос по счётчику и вопрос по обращению дают кнопку повторной подачи (10.5). Реестр собирается из хранилищ своих фич (`features/registry`).
- ✅ 18б. Обращения (`/appeals`): 13 тем и подтемы (11.1), форма с адресом из объектов, описанием, контактами, файлами и временем нарушения для тем про отсутствие и качество услуги (11.2, 11.3). Организацию находим по теме и адресу, иначе региональное управление ЖКХ (11.4); номер и сразу передача исполнителю (11.5); для регионального управления показывается номер в системе электронных обращений (11.6, демо). 10 статусов ТЗ, переписка в истории, ответ на вопрос возвращает обращение в рассмотрение, закрыть может человек (11.7, 11.8). Решения организации — демо-панель на странице обращения.
- ✅ 18в. Уведомления (`/notifications`): колокольчик в шапке с числом непрочитанных, страница истории с фильтром «все / непрочитанные», отметкой «всё прочитано», способом и результатом доставки (16.1–16.4). Список не хранится отдельно: уведомления читаются из историй объектов, заявок, договоров, показаний, платежей и обращений (`notifications/domain/notifications.ts`), поэтому не расходятся с ними; «срок передачи показаний» (с 20-го числа, если за месяц ничего не передано) и «приближается поверка» (за 60 дней) считаются от приборов. Тексты в ru и kk по событию. Не сделано: «формирование начислений» и «появилась задолженность» (нужны данные поставщика, придут с бэкендом), настоящая отправка по почте и SMS, шаблоны для администратора (этап 19). В шапке при крупном шрифте на ноутбуке имя входа заменяется значком, длинное имя обрезается.
- 18г. Кабинет организации (отдельный раздел, права по организации): реестры заявлений, договоров, показаний, обращений, начислений; карточка заявления с действиями (проверить, вернуть, отклонить с причиной, согласовать, сформировать договор); календарь работ; журнал действий (12.2–12.7). Расширяем текущий `/operator`.

## Риски и ограничения

- Казахский и английский тексты потребуют вычитки.
- Фото с Wikimedia (CC BY-SA) годятся для теста; для запуска нужны свои или лицензированные.
- Демозаявки в `localStorage` видны только в одном браузере; общая база появится с backend.
- Списки районов и организаций — тестовые, перед запуском сверить с официальными.
