# Сборка на Windows и временный EPERM

При параллельной генерации страниц Windows иногда возвращает `EPERM` на `mkdir` внутри `.next`, хотя права разрешают запись. 26 октября 2026 года диагностический запуск воспроизвёл три таких отказа; та же операция для каждого пути прошла через 100 мс, после чего Webpack успешно собрал 366 страниц.

`pnpm build` запускает `scripts/build.mjs`. На Windows он подключает `scripts/windows-build-fs.mjs` к Node.js и дочерним процессам Next.js. Сборщик остаётся стандартным (Turbopack), аргументы командной строки передаются Next.js. На других ОС дополнительный модуль не загружается.

Исправление повторяет только асинхронный `mkdir` с `recursive: true`, только для `EPERM` и только внутри `.next` этого проекта. Максимум три повтора с паузами 50, 100 и 200 мс. После этого ошибка возвращается вызывающему коду. `EACCES`, другие ошибки и операции вне `.next` не перехватываются. Файлы зависимостей и права Windows не меняются.

Четыре сценария `pnpm test:build-tools` проверяют временные и постоянные ошибки, границы пути, остальные ОС, передачу аргументов и сохранение результата. Они включены в `pnpm check`.

У локальной установки pnpm 11 отличается режим хранилища от сохранённых зависимостей. `verifyDepsBeforeRun: warn` оставляет предупреждение видимым и предотвращает автоматическую переустановку `node_modules` перед каждой командой. Это не отключает форматирование, ESLint, проверку типов, тесты или сборку. После изменения зависимостей по-прежнему нужно явно выполнять `pnpm install`; в этой доработке зависимости и lock-файлы не обновлялись.

Next.js также может отдельно сообщать `SecurityFatalError` с рекомендацией обновления. Это отдельная проверка, она не отключалась и не является `EPERM`.

Проверка 26 октября 2026: обычная команда `pnpm check` завершилась с кодом 0 — форматирование, ESLint, типы, четыре теста исправления, 438 тестов фронта и генерация всех 366 страниц прошли. Интерфейс не изменялся, e2e не запускался.
